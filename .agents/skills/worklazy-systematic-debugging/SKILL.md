# WorklazyTools 국소 디버깅

## 적용 범위

기본 사용자는 Codex 구현 담당 Sol이다.
다른 담당자가 조사에 사용하더라도 제품 수정 권한이 추가되지는 않는다.

현재 프로젝트 규칙과 승인된 작업 범위 안에서 사용한다.
이 스킬은 새 계획·전체 감사·배포를 시작하는 지시가 아니다.

다른 스킬이나 서브에이전트를 자동으로 호출하지 않는다.
특히 TDD와 완료 검증 스킬을 필수 후속 절차로 연결하지 않는다.

## 1. 문제를 좁힌다

다음 내용을 기존 작업 기록에 짧게 정리한다.

- 기대 동작과 실제 동작.
- 문제가 발생하는 입력·조작·환경.
- 재현 여부와 관련 오류·로그.
- 이번에 수정하도록 승인된 범위.

이미 제공된 재현 절차와 로그를 우선 활용한다.
같은 내용을 사용자에게 다시 묻거나 새 문서를 반복 생성하지 않는다.

재현되지 않으면 확인하지 못한 조건을 명시한다.
추정한 원인을 확인된 사실처럼 쓰지 않는다.
권한·환경·테스트 도구의 실패와 제품 결함을 구분한다.

## 2. 관련 경로에서 원인을 조사한다

오류 위치, 호출 경로, 최근 diff, 설정·의존성 변경을 확인한다.
정상 동작하는 유사 경로가 있으면 차이를 비교한다.

관련 함수와 그 입력·출력·소비자부터 읽는다.
공용 코드나 다른 기능으로 영향이 이어지는 근거가 있으면 범위를 넓힌다.
파일 이름이나 수정 줄 수만으로 영향이 작다고 단정하지 않는다.

관련 결정·기각 이력은 검색해서 해당 부분을 읽는다.
과거 기록이나 저장소 전체를 매번 통독하지 않는다.

여러 구성 요소가 연결된 문제라면 의심되는 경계부터 확인한다.
모든 계층에 일괄적으로 로그를 추가하지 않는다.

진단 정보에는 사용자 문서 내용, 암호, 인증정보,
식별 가능한 파일명·경로 등 민감한 값을 남기지 않는다.
필요하면 합성 입력을 사용하고, 단계·자료형·건수·시간 등
문제 확인에 필요한 비민감한 정보만 기록한다.

## 3. 가설 하나를 최소 실험으로 확인한다

“관찰한 Y 때문에 X가 원인으로 의심된다”처럼 근거를 적는다.
확인된 원인과 아직 검증하지 않은 가설을 구분한다.

서로 무관한 변경을 한꺼번에 넣지 않는다.
가설을 구분할 수 있는 가장 작은 실험을 먼저 수행한다.

실험 결과가 가설과 다르면 원인을 재검토한다.
실패한 수정을 그대로 쌓아 올려 다음 수정을 시도하지 않는다.
자신이 만든 실험 변경과 사용자·다른 작업의 변경을 구분한다.

검사 결과가 의심스러우면 테스트 대상·입력·실행 환경을 확인한다.
예전 빌드, 잘못된 화면, 0건 실행으로 현재 코드를 판정하지 않는다.

## 4. 승인된 범위에서 원인을 수정한다

원인과 직접 관련된 최소 변경을 구현한다.
같은 원인을 해결하려면 여러 파일이 필요할 수 있으므로
기계적으로 한 파일·한 줄로 제한하지 않는다.

무관한 리팩터링, 이름 정리, 새 기능을 섞지 않는다.
출력 계약·데이터 보호·큰 의존성 변경이 필요하면
관련 부분을 조정자에게 전달하고 임의로 확장하지 않는다.

생성물과 벤더 파일은 직접 수정하지 않는다.
원본 스크립트·입력·설정에서 해결한다.

재현 방법은 다음 순서로 선택한다.

1. 해당 결함을 잡는 기존 테스트나 재현 절차.
2. 기존 환경에서 추가할 수 있는 작은 회귀 테스트.
3. 자동화가 부적절한 시각 문제의 구체적인 수동 재현과 캡처.

파일 처리·출력 정확성·데이터 손상처럼 중요한 동작은
가능한 한 자동 회귀 테스트로 남긴다.
단순 시각 문제를 이유로 새 테스트 프레임워크나
대규모 테스트 환경을 도입하지 않는다.

새 회귀 테스트는 가능하면 수정 전 실패와 수정 후 성공을 확인한다.
이미 수정한 상태라면 원본 작업트리를 무작정 되돌리지 않는다.
필요한 비교는 격리된 복사본 등 안전한 환경에서 수행한다.

테스트보다 먼저 코드를 작성했다는 이유만으로
완성된 코드를 삭제하고 처음부터 다시 작성하지 않는다.

## 5. 수정한 경로와 직접 영향받는 부분을 검증한다

수정된 소스로 원래 실패 경로를 실제로 다시 확인한다.
관련 경계조건과 공용 소비자 중 영향받는 부분을 함께 검사한다.

검증 범위와 최종 통합 검사는 PROJECT_RULES.md를 따른다.
이 스킬이 별도의 전체 회귀 의무를 추가하지 않는다.

다음을 이유로 전체 검사를 시작하지 않는다.

- 디버깅 스킬을 사용했다는 이유.
- 수정이 끝났다는 이유.
- 구현자에서 검수자로 담당자가 바뀌었다는 이유.
- 이전 검증 결과가 다른 대화나 세션에 있다는 이유.

이전 결과는 관련 코드·설정·의존성·입력·환경에
변경이 없다는 근거가 있을 때만 재사용한다.
이번 수정으로 무효가 된 검사는 다시 실행한다.

실행 명령·대상·결과·산출물 위치를 남긴다.
0건 실행, 미실행, 실행 불가, 실패를 통과로 처리하지 않는다.

검수자는 유효한 결과를 확인하고,
중요한 위험·의심스러운 결과·핵심 경로를 독립 재현한다.
구현자가 실행한 검사 전체를 일괄 반복하지 않는다.

## 6. 실패한 시도는 증거를 정리하고 재평가한다

새 증거 없이 같은 가설의 수정만 반복하고 있다면 멈춘다.
현재까지 확인한 사실, 배제한 가설, 남은 질문을 정리한다.

수정 실패 횟수만으로 구조 문제라고 단정하지 않는다.
재현 조건, 검사 환경, 상태 잔존, 잘못된 전제를 먼저 재검토한다.

구조 변경이 필요한 구체적인 근거가 있거나
승인 범위를 벗어난 결정이 필요하면 Claude에게 전달한다.
단순 구현 선택마다 사용자에게 결정을 요구하지 않는다.

원인이 확인되지 않았다면 “원인 미확인”으로 보고한다.
완화 조치를 했다면 근본 해결과 구분한다.
문제가 해결됐다는 근거가 없으면 해결됐다고 보고하지 않는다.

## 종료와 보고

원래 결함과 직접 영향받는 경로를 확인하면
새 근거 없이 추가 조사·전체 회귀를 계속 만들지 않는다.

기존 작업 기록에 다음을 간결하게 남긴다.

- 원인: 확인된 사실과 남은 가설.
- 수정: 변경한 부분과 영향 범위.
- 검증: 새 실행과 유효한 결과 재사용.
- 제한: 미확인·실행 불가·남은 결함.
- 후속: 최종 통합 검사나 별도 처리할 사항.

이 스킬의 종료는 국소 디버깅 종료다.
작업 전체의 완료·커밋·배포 조건을 대신하지 않는다.
