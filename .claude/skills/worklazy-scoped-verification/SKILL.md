# WorklazyTools 변경 범위 기반 검증

## 목적과 적용

변경 영향에 맞는 검사를 선정하고, 유효한 결과를 재사용하며,
필요한 독립 검수만 수행한다. 검사를 무조건 줄이는 절차가 아니다.

PROJECT_RULES.md와 해당 역할 문서를 확인한다.
같은 세션에서 확인한 파일이 바뀌지 않았으면 반복해서 읽지 않는다.
이 스킬은 승인 범위·역할·필수 완료 기준·실행 권한을 변경하지 않는다.
현행 규칙과 충돌하면 조용히 우회하지 말고 충돌 항목을 보고한다.
다른 스킬·모델·서브에이전트 호출을 필수 후속 단계로 만들지 않는다.

## 1. 현재 맡은 역할만 수행한다

- Claude: 총괄로서 검사 범위·완료 조건을 정하고 요구사항·제품 원칙·범위·누락·증거 적정성을 감사하며 최종 판정·취합한다.
- 지정된 구현자(Sol 또는 Muse): 구현 후 필요한 검사를 실행하고 증거를 남긴다.
- Astra: 계획의 기술 검토·반박과 결과 검수를 맡아 변경 내용·증거를 확인하고 필요한 부분을 독립 재현한다. Claude의 총괄·감사 역할을 대체하지 않는다.
- Gemini: 위임된 화면·조사 범위의 증거를 제공한다.

한 번 호출됐다고 네 역할을 모두 순회하지 않는다.
검수 담당에게 제품 코드 수정·커밋·배포 권한이 추가되지 않는다.
승인된 작업의 범위 선정은 기존 지시서에서 수행한다.
승인되지 않은 새 구현 계획을 이 스킬로 시작하지 않는다.
`!계획만!`에서는 같은 수준의 기술 검토·반박을 거쳐 검증 계획과 정본을 완성하되 구현 대기로 끝낸다. 미래의 구현 검사 미실행을 현재 계획의 결함으로 취급해 제품 구현이나 전체 회귀를 시작하지 않는다.
명시적 구현 허가가 기록되기 전에는 코드·테스트·설정을 수정하지 않는다. 관련 세션을 `-c`·`-s`로 재개하거나 `--fork`로 분기해도 이 제한은 유지된다. 상세 세션 선택은 공통 규칙과 런북을 참조한다.

## 2. 입력과 기준 상태를 확인한다

다음 정보는 지시서·diff·기존 검증 기록에서 먼저 찾는다.

- 작업 목표, 변경 범위, 제외 범위, 필수 완료 기준.
- 기준 커밋과 현재 소스의 차이.
- staged·unstaged·관련 untracked 파일을 포함한 실제 작업 상태.
- 기존 검사 결과의 대상·환경·로그·산출물.

HEAD가 같아도 작업트리가 다르면 동일 소스로 간주하지 않는다.
검사 대상에 필요한 미커밋 변경과 입력은 diff·파일 해시·복사본 등
상황에 맞는 최소 자료로 식별한다. 비밀값은 기록하지 않는다.
매 라운드 저장소 전체 파일의 해시를 새로 계산할 필요는 없다.
기존 결과에 접근할 수 없으면 재사용 가능으로 추정하지 않는다.

## 3. 변경에서 검사 대상으로 연결한다

현재 package.json, 테스트 진입점, 관련 설정을 읽고
실제로 존재하는 명령과 대상 선택 방법을 확인한다.
존재하지 않는 스크립트·필터 옵션을 만들어 사용하지 않는다.

변경 파일에서 다음으로 이어지는 직접 영향 관계를 확인한다.

- import·호출·이벤트·상태와 해당 소비자.
- 공용 CSS·컴포넌트·테마·언어 문구.
- 파서·변환·정렬·직렬화와 출력 계약.
- 생성기·빌드·의존성·런타임·캐시·배포 설정.

실제 연결 근거가 있는 곳으로 범위를 넓힌다.
파일 수·수정 줄 수·확장자만으로 영향이 작다고 단정하지 않는다.
반대로 무관한 기능까지 일괄 감사하지 않는다.

검사는 다음 네 범주로 나눈다.

| 범주 | 판정 기준 |
|---|---|
| 이번에 실행 | 변경된 동작, 무효화된 결과, 필요한 독립 재현 |
| 결과 재사용 | 실제 증거가 있고 관련 입력·조건이 바뀌지 않은 검사 |
| 최종 통합 | 필요하지만 지금 단계에서는 미뤄도 되는 필수 검사 |
| 적용 대상 아님 | 이번 변경과 영향 관계가 없는 검사 |

최종 통합으로 미룬 검사와 적용 대상이 아닌 검사를 혼동하지 않는다.
판정이 불명확하면 좁은 정적 확인·대표 경로 검사부터 수행하고 판단한다.
확인 후에도 광범위한 위험을 한정할 수 없으면 근거를 남기고 확장한다.

## 4. 기존 결과의 유효성을 검사별로 판정한다

재사용은 다음을 확인한 경우에만 허용한다.

- 해당 실행의 명령·옵션·대상과 결과를 확인할 수 있다.
- 대상 소스·테스트·설정·관련 의존성·fixture를 식별할 수 있다.
- 현재 변경이 그 검사의 입력과 동작에 영향을 주지 않는다.
- 관련 실행 환경과 브라우저·런타임 조건이 달라지지 않았다.
- 필요한 로그·결과 파일·캡처가 존재하고 실행 범위를 뒷받침한다.

소스·fixture·검사기·환경 등 유효성 조건이 바뀌면
영향받은 결과만 무효화하고 다시 실행한다.
증거가 유실되거나 기준 소스를 식별할 수 없으면
해당 필수 검사를 미확인으로 처리하고 필요한 범위에서 재실행한다.

결과가 다른 세션에서 생성됐거나 담당자가 바뀌었다는 이유만으로
무효화하지 않는다. 반대로 단순한 “통과했다”는 보고만 재사용하지 않는다.
이전 통과는 현재 수정된 경로의 확인을 대신하지 않는다.
재사용 결과는 “재사용”으로 적고, 새로 실행했다고 쓰지 않는다.

## 5. 필요한 검사만 실행한다

구현 중에는 국소 단위 테스트·신고 재현·관련 스모크부터 실행한다.
공용 소비자에 영향이 있으면 그 소비자를 추가한다.
현재 소스로 만든 산출물이 필요한 검사는 먼저 그 산출물을 준비한다.
오래된 빌드를 대상으로 검사한 뒤 현재 소스가 통과했다고 쓰지 않는다.

범위 필터를 사용하면 실제 선택 대상과 실행 건수를 확인한다.
필터 미지원·0건 실행·중도 종료를 정상 통과로 처리하지 않는다.
범위가 너무 넓은 기존 테스트를 분리해야 하더라도,
검수 담당이 임의로 테스트 코드를 수정하거나 기준을 약화하지 않는다.
대체 검사가 완료 기준을 충족하지 못하면 그 차이를 남긴다.

공통 규칙의 최종 통합 검사는 작업 묶음의 최종 후보에서 확인한다.
수정마다 최종 통합 검사 전체를 선행하지 않는다.
검사 후 추가 수정이 생기면 무효화된 검사만 다시 실행한다.
CI·브랜치 보호·배포 필수 검사를 이 스킬로 비활성화하거나 우회하지 않는다.

새 결함이 나오면 먼저 재현·영향을 확인한다.
실패 하나를 이유로 무관한 전체 회귀를 추가하지 않는다.
검사 대상 파일·작업 공간이 실행 도중 바뀌었다면
영향받은 결과를 혼합된 상태의 결과로 표시하고 다시 확인한다.

### 병렬 구현·통합 후보의 검증

PROJECT_RULES.md의 「독립 작업의 병렬 구현」을 따른다.
각 결과에 작업 ID·구현자·브랜치/worktree·검사한 커밋/빌드를 연결한다.
로그·캡처·브라우저 세션·서버 포트·fixture·임시 경로를 작업별로 분리한다.
분리 옵션이 없는 고정 자원이나 성능 측정이 서로 영향을 주는 검사만 순차 수행한다.

각 구현자는 자기 변경 범위를 검사하고 공통 최종 검사는 통합 후보에서 취합한다.
두 브랜치의 통과 기록을 합쳐서 최종 후보의 통과로 표시하지 않는다.
공유 계약·연결 경로·충돌 해결과 변경된 빌드 입력을 기준으로
무효가 된 결과·추가 검사·그대로 재사용할 결과를 구분한다.
다른 빌드의 산출물을 최종 후보 빌드의 증거로 바꾸어 적지 않는다.
통합이라는 이유만으로 무관한 전체 회귀를 추가하지 않는다.

구현자는 자기 작업 기록만 작성하고, 통합 담당이 공통 기록을 취합한다.
검수 담당은 구현·통합 권한을 얻지 않으며, 모델이 바뀌었다는 이유만으로
이미 유효한 검사 전체를 다시 수행하지 않는다.

## 6. 시각 검사는 영향 있는 조합으로 제한한다

화면·언어·테마·화면 크기·상태 중 변경 영향을 받는 조합을 선정한다.
긴 문구, 초기 화면, 파일 처리 후, 스크롤 하단 등 필요한 상태를 포함한다.
같은 컴포넌트라도 소비자별 배치·상태가 다르면 대표성이 있는지 확인한다.

선정한 화면은 실제로 열람한다.
캡처 생성이나 자동 픽셀 비교만으로 시각 검토를 완료했다고 하지 않는다.
선정 범위, 실제 열람 범위, 미확인 범위를 구분한다.
구현 원인은 화면의 증상만으로 단정하지 않는다.

민감한 사용자 파일 대신 합성·비식별 입력을 우선 사용한다.
빌드·로그·캡처는 지정된 임시 공간이나 검수용 복사본에 둔다.
테스트가 저장소 내부 경로를 요구하면 복사본 안의 경로를 사용한다.
소스 보호와 실제 파일·네트워크 권한은 별도로 확인한다.

## 7. 독립 검수는 증거 확인과 필요한 재현으로 한다

Astra는 완료된 작업 묶음의 diff와 지시서 이행 여부를 먼저 확인한다.
실제 구현자가 남긴 로그·대상 소스·실행 범위·판정 결과를 대조한다.

추가 재현은 다음에 집중한다.

- 파일 손상·정보 유출·핵심 출력처럼 영향이 큰 변경.
- 누락·모순·0건 실행·대상 불일치 등 이상 징후가 있는 결과.
- 구현자가 확인하지 않은 중요한 경계조건.
- 신뢰성을 확인할 필요가 있는 핵심 표본.

같은 전체 검사를 복제하는 것으로 독립 검수를 대신하지 않는다.
일상적인 전체 검사 중복 없이도 diff·논리·증거를 검토한다.
검수에서 추가한 검사의 이유와 범위를 남긴다.

신규 결함, 기존 결함, 이번 변경으로 악화된 기존 결함을 구분한다.
구분할 근거가 부족하면 발생 시점 미확인으로 적는다.
중대한 결함의 차단 여부는 발생 시점과 별도로 판정한다.
취향·비필수 개선을 결함이나 배포 차단 사유로 바꾸지 않는다.

### Claude 감사와 추가 반박

Astra의 기술 검수 소견과 구현자의 증거는 Claude의 감사·최종 판정에 전달한다. Claude는 요구사항·제품 원칙·범위·누락·결함 귀속·증거 적정성을 확인하되 유효한 검사를 전부 반복하지 않는다.
기본 1+1회는 반박의 상한이 아니다. 새로운 근거·구체적 반례·수정된 계획·추가 확인 가능한 차단 쟁점이 있으면 해당 쟁점만 더 검토한다. 횟수나 한도 때문에 통과시키지 않고, 새 근거 없는 반복은 다른 판별 방법으로 전환한다.
추가 반박이 있어도 같은 전체 검사를 새로 요구하지 않는다. 요청 모드와 검사 결과의 현재 유효성에 따라 필요한 확인만 추가한다.

## 8. 기록은 작업당 한 곳에 유지한다

기존 작업지시서의 검증 절을 갱신한다.
적절한 기록이 없으면 허용된 오프라인 작업 공간에 하나만 만든다.
별도 대시보드·새 테스트 프레임워크·필수 자동화 스크립트를 만들지 않는다.

각 검사에 필요한 최소 기록은 다음과 같다.

| 검사·범위 | 실행/재사용/이월/대상 아님 | 근거·대상 상태 | 결과·증거 위치 |
|---|---|---|---|

실행 항목에는 명령·옵션, 관련 환경, 대상 상태,
종료 코드 또는 수동 관찰 결과, 필요한 로그·캡처 위치를 연결한다.
긴 명령과 원시 로그는 표 안에 복제하지 않고 기존 기록을 참조한다.
이미 확인한 환경 정보는 바뀌지 않았으면 다시 수집하지 않는다.
병렬 검수자는 같은 기록을 동시에 덮어쓰지 않고 결과를 조정자에게 전달한다.

결과는 통과·실패·미확인·실행 불가·적용 대상 아님을 구분한다.
핵심 측정과 기각 이유만 장기 기록으로 남긴다.
원시 로그나 정상 결과의 반복을 상시 규칙 문서에 추가하지 않는다.

## 종료 기준

종료는 요청 모드에 맞춰 판정한다. `!계획만!`에서는 필요한 반박과 검증 계획·정본화가 끝나면 「정본화 완료·구현 대기」로 보고하고 종료한다. 구현 허가가 없으면 다음 구현 단계로 넘어가지 않는다. 차단 쟁점이 남으면 「검토 중·미해결」로 남긴다.
구현이 허가된 단계는 해당 단계의 필수 검사가 충족되고 차단 결함이 없으면 종료한다.
구현 중 이월한 필수 검사는 최종 통합에서 빠짐없이 회수한다.
미확인 필수 항목이 남으면 전체 완료로 표시하지 않는다.
목표·허용오차·기대값을 낮춰 통과를 만들지 않는다.

완료 보고는 다음 네 가지로 끝낸다.

- 이번에 확인한 범위와 결과.
- 재사용한 결과와 그 근거.
- 미실행·실행 불가·이월 사항.
- 차단 결함 유무와 이번 단계의 완료 여부.

새로운 결함·위험·요청 없이 감사와 전체 회귀를 추가하지 않는다.
이 스킬의 종료는 커밋·push·배포 승인을 의미하지 않는다.
