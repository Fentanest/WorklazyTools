# Word 변경 추적 DOCX 성능 재측정

R30은 문서 비교의 변경 추적 DOCX 완료 시간이다. 문서→PDF 변환과 별도 경로다.
원래 Windows 50쌍 코퍼스(w010/w046 등)와 측정 하네스는 현재 Linux 자료에서 확인하지 못했다.
아래 측정은 **원 코퍼스 미사용**이며 과거 1.34배/2.40배나 R30 통과 여부와 직접 비교하지 않는다.
이전 추출/생성 프로파일은 `docs/review-notes.md`의 2026-10-25~26 기록을 참고한다.

## 재현

결과 경로는 매 실행 새 빈 폴더를 사용한다. 기존 결과를 새 실행의 통과로 오인하지 않도록
비어 있지 않은 결과 폴더는 거부하고 이전 증거를 보존한다.

기준 커밋의 `src/features/word-compare/`에서 `compare.py`, `accept_revisions.py`,
`tracked_docx.py`, `formatting-policy.json`, `word.worker.ts`를 별도 기준 폴더에 보존한다.
`npm ci` 후 자기 작업 공간에서 실행한다(결과는 제품 폴더 밖의 명시적 경로 권장).

```sh
python3 -B scripts/benchmark-word-compare.py \
  --output /tmp/word-r30-measurement \
  --baseline /tmp/word-r30-baseline --runs 3
```

입력은 저장소 oracle 6쌍과 결정적으로 생성한 합성 4쌍이다. 합성 큰 문서는
1,800문단×8런, 별도 QName 입력은 문단별 네임스페이스 선언을 포함한다.
`tests/helpers/word-performance-fixtures.py`가 입력·사양·SHA-256 manifest를 만든다.
원본 문서 내용과 생성 결과를 외부로 보내지 않는다.

하네스는 기존 `word-worker-batch` 검사처럼 **실제 Worker 원문과 실제 Pyodide/TS 모듈**을
Node에서 실행한다. 런타임 준비·수락·추출/인코딩·전송 복원·비교·manifest 직렬화·생성을 분리한다.
각 쌍을 별도 프로세스에서 실행하고 전후 순서를 교대해 잔류 WASM 메모리/순서 편향을 줄인다.
주 측정은 기존 기록 먼저 수락·서식/표/메타데이터 포함 모드다. 수락하지 않는 모드와
서식 마스크/이벤트 보존은 별도 Word 회귀 검사로 확인한다.
`workerMs`는 준비된 Pyodide에 Worker가 진입한 때부터 완료까지(파이썬 스크립트 준비 포함),
`coldTotalMs`는 여기에 Pyodide 초기화를 더한 값이다. Node/TS 모듈 시작·DOM 렌더 시간은 포함하지 않는다.

각 실행에서 실제 추출 2회·생성 1회·양수 결과를 요구한다. 화면·복원 모델·manifest의 해시와
생성 ZIP의 모든 파트 이름/내용 해시를 전후 및 반복 간 대조한다. ZIP 포장 시각은 비교하지 않는다.
리비전 시각은 고정한다. 입력 해시 불일치·출력 차이·실패는 중단하며 누락/0건을 통과시키지 않는다.

RSS는 부모가 `/proc`에서 약 20ms 간격으로 관측한다. 초기화를 포함한 프로세스 최고와
수락~생성 구간의 관측 최고를 구분한다. 실제 순간 최고를 보장하는 값은 아니다.
WASM 힙은 반환/축소되지 않을 수 있어 속도 개선을 메모리 감소로 해석하지 않는다.
프로파일용 `--profile=true` 실행은 cProfile 비용이 있으므로 시간 비교 표본에서 제외한다.

## 적용한 국소 개선

`_styled_tokens`는 동일 런의 서식을 문자마다 깊은 복사하던 것을 런당 한 번의 독립 스냅샷으로 공유한다.
토큰 소비자는 이 스냅샷을 읽고, `_token_run`/투영 함수는 변경 전에 계속 독립 복사한다.
추출 원천 목록·공유 계약·출력 형식·수락 정책과 보존/복구 구조는 바꾸지 않는다.
폰트 이름은 OOXML 속성으로 보존하며 이 Worker에서 폰트 파일을 로드하거나 페이지를 렌더하지 않는다.
화면 렌더 비용은 별도 브라우저 관찰과 구분한다.
